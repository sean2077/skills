# Development guide

This page owns contributor commands, verification, generation, and this repository's release procedure. [Architecture](architecture.md) identifies the source to edit. [Validation CI](../.github/workflows/validate.yml) is the sole executable inventory of the complete suite.

## Prerequisites

Use Git with real symlink support, Python 3.11 for the primary suite, and Bash on Linux/macOS or Git Bash on Windows. Installer checks also need Node.js/`npx`; shell validation needs ShellCheck. Install pinned dependencies with `python -m pip install -r requirements-validation.txt`.

Consumer scaffold/runtime code targets Python 3.8+, but the dedicated CI floor job exercises only selected checks, including generated runtimes and release analysis. Do not certify every script from that job. Set `PYTHONUTF8=1` and `PYTHONDONTWRITEBYTECODE=1` so encoding and generated bytecode do not contaminate payload checks.

## Worktree flow

Honor the user's session entry and resolve the task checkout, revision, authority chain, and lifecycle owner. Reuse an assigned linked worktree. The [managed rule](../AGENTS.md#worktree-per-change-hard-rule) prohibits primary-worktree edits, including docs, not primary-checkout planning.

```bash
task="/absolute/path/to/task-checkout"
git -C "$task" rev-parse --show-toplevel
git -C "$task" status --short --branch
git -C "$task" rev-parse HEAD
# Run subsequent checks with cwd set to "$task".
```

Only when no checkout is assigned and scaffold owns creation, run `bash .agents/tools/worktree.sh new <name>` from the primary checkout. Verify the intended remote base: the helper's local trunk is not proof of latest main. A shell `cd` does not reload host guidance or permissions. Pass peers the absolute checkout and reviewed revision; see [workspace context](../skills/agent-scaffold/references/workspace-context.md).

For a PR/MR, publish the task branch and verify the actual change request. Do not use `done` as an implicit merge or cleanup: `done --dir <absolute-wt>` merges, pushes, and removes a scaffold-owned worktree only with explicit authorization. External owners retain lifecycle control. Leave a worktree before removal; Windows processes may keep it locked.

## Select checks by changed surface

| Changed surface | Focused evidence |
|---|---|
| Repository documentation only | Whitespace, changed links/anchors and reader routes; `validate_skills.py`; inspect or safely execute changed commands and identify unverified claims |
| Skill entry point, references, frontmatter, route, manifest, or layout | Catalog health/validation and fixtures, official `skills-ref`, applicable payload/contracts; installer smoke tests when distribution changes |
| Shared/generated runtimes | Both generator `--check` commands and affected workflow, P0, hardening, private-skill, and evaluation tests |
| Scaffold source or managed projections | Core/workspace/selection/layout-preservation tests, static shell gate, throwaway E2E, real symlinks, and platform matrix |
| Shell scripts | Targeted behavior tests and ShellCheck |
| Evaluation manifests/adapters | Suite/result validation, adapter/oracle regressions, scope/cost/isolation checks; live runs require separate configuration and authorization |
| Release/version logic | Planner/extractor fixtures, release execution tests, and exact tagged snapshot/workflow review |

Shared routing, validators, generators, installers, scaffold, contracts, or CI changes require the complete applicable suite. Wording-only changes do not acquire an evaluation or independent-review gate. [Documentation verification](documentation-maintenance.md#evidence-and-verification) explains the limits of catalog link checks.

## Starting local checks

From the task checkout in Bash, this is a **starting check**, not the full suite:

```bash
(
  set -eo pipefail
  export PYTHONUTF8=1 PYTHONDONTWRITEBYTECODE=1
  python -m pip install -r requirements-validation.txt
  python scripts/catalog_health.py
  python scripts/validate_skills.py
  git diff --check
  git diff --cached --check
)
```

Run the affected tests from the table above. For full verification, use the commands in [validation CI](../.github/workflows/validate.yml), adapting runner-specific temporary paths for local use. CI owns the complete inventory; do not maintain another copy here.

CI covers Ubuntu, macOS, and Windows, asserts real symlinks/platform shells, byte-compares installed regular-file payloads, and exercises the Python 3.8 floor. Report only environments/checks actually run. Offline evaluation validates plumbing, not model effectiveness.

## Writing tests

Tests use standard-library `unittest`: catalog fixtures in `scripts/test_*.py`, other tests in `scripts/tests/`. Run a file with `python <file>`; run the two P0 modules with `python -m unittest scripts.tests.test_p0_agent_workflows scripts.tests.test_p0_hardening`.

CI has **no automatic test discovery**. Register a new test file in the applicable executable CI step; update this guide only when contributor procedure changes. Add floor-sensitive tests to the Python 3.8 job when needed.

Use temporary real Git repositories, the actual installer, and real symlinks for owned behavior. Mock external services, such as release publication through `gh`. Skip only unavailable platform capabilities and name the reason. Assert observable bytes, exit codes, reports, and Git state, not incidental English wording. A regression should fail without its fix. Test-first work is a scoped project/user choice, not a repository-wide requirement; see [harness principles](harness-constraint-policy.md#choosing-guidance-and-machinery).

### Scaffold coverage

| Question | Owning evidence |
|---|---|
| Does installation preserve existing layouts, project prose, staged/dirty state, and read-only modes? | `scripts/tests/test_project_conventions.py`, core/workspace tests, and E2E |
| Are missing/legacy/all/none selections, opt-outs, invalid inputs, and repeated runs handled correctly? | `scripts/tests/test_guidance_selection.py` and real installation tests |
| Is project guidance usable and linked without reviving retired templates? | [Task outcome fixtures](../evals/tasks/README.md); bounded artifact/reader-route oracles |
| Does a model choose the intended route or report a selection decision? | [Routing probes](../evals/agent-skills/README.md); not actual onboarding dialogue or completed guidance |

A saved selection is a preference, not semantic completion. The CLI does not read stdin; runtime-only callers must not invent an onboarding answer. Reference actions test oracles, not live Agent adaptation. Preserve source-owned testing/TDD/coverage clauses; guidance fixtures do not establish prose quality or actual RED/GREEN traces.

## Evaluation evidence

Use [routing probes](../evals/agent-skills/README.md) for stated decisions and [task outcomes](../evals/tasks/README.md) for observed edits, calls, and test sequences. Those guides own commands, adapter contracts, controls, and measurement limits. Commit intended candidate/manifests before revision-pinned execution; dirty edits are not the treatment. Unknown usage stays unknown.

### Optional skill-verifier

For substantive skill changes or uncertain evidence, give the project `skill-verifier` the absolute checkout, pinned revision, diff/dirty snapshot, scope, acceptance, and captured results. It reviews sources and evidence without executing commands or editing them. For example:

> Review <revision> in <absolute-task-checkout> and the supplied results. Find regressions or assertions that accept wrong output; return findings and proposed checks without modifying sources or executing commands.

Its sources are [instructions](../.agents/subagents/skill-verifier/instructions.md) and [metadata](../.agents/subagents/skill-verifier/metadata.json). The parent captures evidence, runs proposed checks in an authorized environment, resolves findings, and owns delivery. This opt-in project role is not a catalog install or approval authority; model/effort remain host-selected.

Configured tools and `read-only` settings do not prove live enforcement; check effective parent overrides and [dated host evidence](compatibility.md#project-subagent-definitions-2026-09-22). Worktrees/clones are not process sandboxes. Use effective filesystem/network/credential isolation when required.

An explicitly blind/cold-reader comparison needs a fresh instance with only task, acceptance, and anonymized artifacts, separate from baseline/treatment execution. Reusing a source reviewer or leaking project identities is not blindness. An optional reader check is not exact-file approval or an automatic gate.

## Generated files

Edit the [canonical source](architecture.md#source-and-generated-ownership), then run only its owning generator and review the diff:

```bash
python scripts/generate_workflow_runtimes.py
python scripts/generate_p0_runtimes.py
```

Rerun the affected `--check` and behavior tests. Refresh scaffold-owned runtime/contract through the catalog skill's `upgrade`, then `verify`. Project skills use `bash .agents/relink-skills.sh`; project subagents use `python .agents/tools/generate-subagents.py` and its `--check`. Commit sources and projections together; do not patch generated files to hide drift.

## Installer checks

From the catalog checkout, `NO_COLOR=1 DISABLE_TELEMETRY=1 npx --yes skills@1.5.17 add . -l` checks discovery only. Actual install smoke tests run from a fresh consumer Git repository, using the catalog path as source; CI compares file inventories/bytes and rejects non-regular payload entries. Repeat remote-source discovery after publishing an intended discovery fix.

[Installer semantics](compatibility.md#installer-semantics) owns scope, option behavior, the audited pin, and removal safety. Inspect top-level `--help`: `add <source> --help` may execute an add flow. Never run project-scope removal from the catalog checkout. Treat a newer pin as an explicit dependency change.

## Release flow

Completion means a verified GitHub Release created by [release CI](../.github/workflows/release.yml), not a planner result or tag push. Before a version bump, tag, or publication, read the installed [release conventions](../.agents/tools/release/README.md); repository-specific rules below override generic defaults. Documentation-only PRs add Unreleased notes but do not bump versions, tag, or publish.

1. Accumulate changes under Unreleased; move release notes into one matching dated section for the supported tag. `.claude-plugin/plugin.json` has no release-version field; do not invent one for a release. Use Conventional Commits without `Co-Authored-By`, including squash titles: the analyzer derives the bump from main's commit subjects (merged commits or the squash title).
2. Validate and merge the release snapshot, verify main CI, and resolve the intended remote main/release commit. CI rejects tags whose commits are not reachable from `origin/main`.
3. Before tagging, analyze with `--release-branch main` on a clean, attached `main` checkout equal to `origin/main`. A task worktree on another branch reports `release-line` attention by design. With release authorization, push an annotated `vX.Y.Z` or numbered `-alpha.N`, `-beta.N`, or `-rc.N` tag (numbers start at 1). Build metadata and arbitrary prerelease labels are unsupported; never move or recreate a tag.
4. Observe reusable validation, tag/commit checks, exact changelog extraction, and workflow-owned publication; do not race it with a manual publisher.
5. Verify the release URL, tag/peeled commit, non-draft/prerelease state, and body matching the tagged changelog. Report failed or unavailable evidence rather than completion at push.

Local analysis is read-only:

```bash
python .agents/tools/release/release-plan.py --repo . --release-branch main --json
```

Schema 2 status `analyzed` means local supported-format analysis, not branch-policy compliance, publishability, or authorization. Derive `--release-branch` from explicit policy and resolve attention before mutation.

The analyzer and [changelog extractor](../.agents/tools/release/extract-changelog.py) are scaffold runtime for the selected `release` domain. Edit canonical sources under `skills/agent-scaffold/assets/runtime/release/`, then refresh with `agent-scaffold upgrade`; the scaffold gate rejects installed drift.
