# Documentation Classification Methods

Different groupings serve different retrieval problems. Compare the ones supported by project evidence.

| Lens | Useful boundary | Trade-off |
|---|---|---|
| Reader role | Different prerequisites, permissions, or outcomes | Shared material can become duplicated across roles. |
| Task or journey | Readers seek a repeatable outcome or incident procedure | Cross-cutting workflows can obscure stable domain ownership. |
| Domain and ownership | Capabilities own distinct meanings, decisions, and lifecycles | Team or source-directory names alone may not express the domain. |
| Product or interface | Readers recognize stable products, APIs, CLIs, or SDKs | Incidental implementation boundaries can churn with refactors. |
| Content purpose | Learning, completing a task, understanding, and looking up facts need different treatment | Separate content types can fragment a small, coherent document. |
| Lifecycle and authority | Proposals, released contracts, generated outputs, and history have different trust rules | Status buckets can hide unresolved ownership. |

For example, a release journey can link preparation, publication, and recovery while each underlying command has one reference page. Operators and integrators can have different entry points to a shared authentication explanation. Two domains using “account” differently may need separate owning definitions.

Evaluate candidate structures with representative reader tasks and documents. Use navigation or generated views for secondary routes to the same canonical information. Frameworks such as Diátaxis, DITA, and domain-driven design can supply useful questions; the resulting structure should fit the project.
